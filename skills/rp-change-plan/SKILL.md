# 科研变更规划

遵循 ResearchPatch 项目协议。读取 current.json、相关子图、原始资料和已有授权，记录 base_revision。

## 影响分析

1. 写清变化是已实际发生，还是仅拟议。记录旧值、新值、来源、作用范围与用户目标。
2. 从直接受影响对象沿依赖关系寻找候选，再检查变化是否真正影响各节点。计算依赖与科学解释分开；语义边未经确认时标“可能影响”。
3. 检查论断所有支持组，区分“证据需要更新”“部分支持丢失”和“存在反证”。先设 needs_check/needs_rerun；尚未重算不能预判结论翻转。
4. 给出不受影响对象和依据，防止全图重做。若文件重命名但内容、身份和引用映射不变，不应自动否定科学结果；需要时只更新来源映射。
5. 只有研究问题、结论范围、创新依据或关键文献支持发生变化时，提出补检索及明确检索目标。技术变动通常无需自动重搜文献。

## 变更单

生成 patch_id 与 base_revision。按表列出 affected/unaffected，并为 actions 写明目标 ID、动作、前置任务、验收条件、预算及待核实信息。论断修订建议保持 proposed，不伪造结果。

默认执行顺序为来源核对 → 必要计算 → 结果验证 → 论断审阅 → 下游图表与文字同步，但只保留本次真正需要的动作。

检查现有授权是否已经覆盖方案。若覆盖，注明授权依据并交 rp-apply-verify；若尚未覆盖，提交具体变更单及一个清楚的决定请求，不让研究员批准抽象“全流程”。

拟议变化只写入变更单，不污染当前事实。变化已经发生时，在当前视图和事件中保留影响提示，即便修复尚未批准，也不把旧结论继续显示为无条件有效。

## 输出

变化事实；影响表；不受影响内容；执行任务与预算；有条件的论断修订候选；已有授权或待决定事项。

验收：每项行动能追溯到触发变化；既无遗漏的确定依赖，也没有无理由的全图更新；变更单与实际执行状态明确分开。
